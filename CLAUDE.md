# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Gravitas is a minimal, no-nonsense alternative to Stremio that consumes Stremio addons. Python + PySide6 (Qt6/QML) + libmpv.

## Commands

All commands run through `uv`.

```bash
uv sync                       # install deps + create .venv
uv run gravitas               # launch the app (needs a display + system libmpv)
uv run pytest -q              # full test suite
uv run pytest tests/presentation/test_player_controller.py::test_play_and_controls -v   # single test
uv run ruff check .           # lint gate
uv run ruff format --check .  # format gate (both ruff gates must pass)
uv run mypy src               # type gate: mypy --strict, on src only
uv run python scripts/build_qml_types.py   # regenerate qml/Gravitas/gravitas.qmltypes after changing a QML-facing Property/Signal/Slot
uv run python scripts/build_native_player.py   # build the Rust engine (native/player/) into the app; the default player once built
(cd native/player && cargo clippy --workspace --all-targets && cargo test --workspace)   # the engine's own gates
```

The three quality gates (`ruff check`, `ruff format --check`, `mypy src`) are expected to pass on every commit. QML has a fourth, run by the test suite (`tests/presentation/test_qml_typing.py`): `qmllint` over every `.qml` with **every** category raised to warning must report nothing, and the committed `.qmltypes` must match the Python it was generated from.

**libmpv is a system dependency, not a pip package.** `python-mpv` only wraps the native `libmpv` and loads it at runtime. Without it installed (`dnf install mpv-libs` / `apt install libmpv2` / `brew install mpv`), the app launches and browses fine but playback raises `PlaybackFailed`. On macOS, Homebrew's lib dir isn't on the dyld fallback path — `mpv_player._ensure_libmpv_discoverable()` extends it in-process before `import mpv`. Windows has no libmpv package at all: drop `libmpv-2.dll` (from an [mpv-dev build](https://github.com/shinchiro/mpv-winbuild-cmake/releases)) on `%PATH%`, or point `GRAVITAS_LIBMPV` at it — the same variable the PyInstaller spec honours. Tests never require libmpv (see the factory seam below).

**Packaging targets: AppImage + Flatpak (Linux), dmg (macOS), Inno Setup installer + portable zip (Windows).** One spec, `packaging/gravitas.spec`, feeds all of them; `.github/workflows/release.yml` runs the four jobs into a single rolling release. The Windows build downloads `libmpv-2.dll` and `yt-dlp.exe` during the spec run (7-Zip or `py7zr` needed for the mpv archive), then `packaging/windows/gravitas.iss` wraps `dist/Gravitas/` into `dist/Gravitas-Setup.exe` and writes the `stremio://` handler into `HKCU\Software\Classes`. Regenerate `packaging/icon/gravitas.ico` with `uv run python scripts/build_ico.py` after editing the SVG.

**The Flatpak repackages a host-built bundle, so the build host's glibc is a floor the sandbox cannot lower.** dist/Gravitas carries every library from the machine that ran PyInstaller; a bundle built on a host newer than `runtime-version` (24.08 is glibc 2.40, 25.08 is 2.42, 26.08 is 2.44) fails to start on a missing symbol *version* — `libc.so.6: version 'GLIBC_ABI_GNU2_TLS' not found` names a symbol, not the cause. The manifest is on 26.08, the first runtime a current-Fedora (glibc 2.43) bundle runs in, so `bash packaging/build_flatpak.sh` works on a dev machine again -- and carries the native engine when it is built, which the release job does not build on Linux yet; the release job itself builds on ubuntu-24.04. The 26.08 Sdk dropped `appstreamcli`, so the manifest leaves the AppStream catalog to flatpak-builder's own compose (1.4+, the host's `appstreamcli`) instead of composing it in `build-commands`. `packaging/build_flatpak.sh` makes that check up front rather than at first launch. **Every Linux packaging job must build the Vulkan bridge before running the spec** (`scripts/build_video_bridge.py`, Qt headers via aqt, matching the wheel's Qt exactly) — the spec bundles it only if it is already there, so a job that skips it silently ships an app pinned to OpenGL.

## Architecture

Strict Clean Architecture. The dependency rule is enforced and must be preserved:

```
presentation  →  application  →  domain  ←  infrastructure
```

- **`domain/`** — pure. `models.py` (frozen dataclasses: `MediaItem`, `MetaDetail`, `Stream`, `AddonManifest`, …), `errors.py` (every error subclasses `GravitasError`), `ports.py` (`Protocol` interfaces: `AddonSource`, `MediaPlayer`, `ProgressStore`, `SettingsStore`, `ExternalIdResolver`, `DebridResolver`). Imports nothing from other layers, Qt, or httpx.
- **`application/`** — use cases (`InstallAddon`, `BrowseCatalog`, `GetDetail`, `ResolveStream`) plus `addon_repository.py` (installed-addon store + cross-addon catalog aggregation with per-addon fault isolation). Depends only on `domain`. **Do not import `infrastructure` here** — `AddonRepository` lives in `application` precisely to keep this rule.
- **`infrastructure/`** — adapters implementing domain ports: `addons/client.py` (httpx `AddonSource`), `addons/parsing.py` (pure Stremio-JSON→model functions, no I/O), `cache/ttl_cache.py` + `cache/network_cache.py`, `progress/sqlite_store.py`, `player/mpv_player.py`. May import `domain` + third-party, never `application`/`presentation`.
- **`presentation/`** — Qt/QML only. `controllers/` (QObject bridges exposing Slots/Signals), `models/` (`QAbstractListModel` subclasses feeding QML), `qml/`. Imports `domain`+`application`; nothing imports it back.
- **`main.py`** — the single composition root. The only place that references concrete adapter classes and wires them into use cases → controllers → the `Gravitas` QML module's singletons.

Data model follows the Stremio addon protocol: addons serve `/manifest.json`, `/catalog`, `/meta`, `/stream`. Metadata and posters come from the addon's own `/meta` (Cinemeta-style) — Cinemeta is bootstrapped as the default addon on startup.

**There are two player engines, and the user picks one in Settings > Player.** `native/player/` is Gravitas' own player (FFmpeg + cpal + libass + libplacebo, or its own Metal renderer on macOS), bound to Python by PyO3 as `gravitas_player` and adapted to the same `MediaPlayer` port by `infrastructure/player/native_player.py`; the setting (`PersistedSettings.video_player`, `"native"` by default, `GRAVITAS_PLAYER=native|mpv` overrides it) selects it at start-up -- a change applies on the next start, because the choice decides the video item and the graphics device -- together with `presentation/video/native_item.py` under the QML name `MpvVideo`. It exists because the hardest limits in this file are mpv's, not ours (Dolby Vision profile 5, track switches that re-read the stream, one render API per platform bridge), and it is built in milestones -- the design and roadmap are in `native/player/README.md`. A copy without the built module plays through mpv whatever the setting says, and the setting says so; the macOS dmg ships the module (the release job builds it and fails if the bundled copy still links Homebrew), and the Windows job builds it with MSYS2 (see the Windows gotcha below); the Linux bundles do not yet. Tracks come back in mpv's `track-list` shape so `infrastructure/player/track_list.py` labels and language-matches for both engines.

**No torrent engine, ever.** The player only receives direct HTTP/HLS URLs. `ResolveStream` filters to `stream.is_direct` and raises `NoStreams` otherwise. Torrent→URL resolution belongs to a future client-side debrid milestone (a `DebridResolver` port stub exists but is unused).

**yt-dlp is an optional system dependency, like libmpv.** `Stream.playable_url` maps a protocol `ytId` (YouTube-backed streams and every `trailerStreams` entry) to a watch URL, which mpv resolves through its `ytdl_hook` — that hook shells out to `yt-dlp`. Without it on PATH, those streams raise `PlaybackFailed` like any other unplayable URL; everything else works untouched.

**Only `movie` and `series` exist here.** The protocol also defines `channel` and `tv`; supporting them would make `MediaType` four-way and turn Gravitas into an IPTV client. `parse_manifest` drops catalogs of those types and logs each one — an addon serving only them installs fine and shows nothing, so the log is the only clue. Deliberate; see the roadmap before "fixing" it.

## Critical gotchas (each cost a review cycle)

- **Async controller slots must use `@qasync.asyncSlot`, not `@Slot`.** PySide6 silently drops the coroutine from a plain `@Slot` async method — it's constructed and never awaited. `CatalogController.refresh` / `DetailController.load` rely on `asyncSlot` so they actually run on the qasync loop. The app runs asyncio on Qt's loop via `qasync`; all HTTP is async httpx.
- **qasync never installs asyncio's async-generator hooks, so `main()` does (`_adopt_asyncgen_hooks`).** `BaseEventLoop` sets them when it starts running; qasync's `run_forever` does not. Without them an async generator left unfinished -- httpcore's response stream behind a cancelled request -- is closed synchronously wherever the garbage collector runs, and the `await` in its cleanup prints "async generator ignored GeneratorExit" or "RuntimeError: no running event loop" from a stack unrelated to the cause. With them its `aclose()` is a task on the loop, as under `asyncio.run`. `tests/test_asyncgen_hooks.py` reproduces the first message without the hooks.
- **Startup ordering is deterministic on purpose.** `Home.qml` does *not* self-refresh on load. `main.py`'s `bootstrap()` installs the default addon, binds its manifest, then drives the first catalog refresh — otherwise the grid refreshes against an empty repo and shows nothing.
- **libmpv is lazy-imported inside `_default_factory`** in `mpv_player.py` (not at module top), so the module and its tests import without libmpv present. `MpvPlayer` takes a `factory` seam — tests inject a `FakeMpv`, so player logic is unit-tested without the native lib. `locale.setlocale(LC_NUMERIC, "C")` must run at `mpv.MPV()` construction time (Qt resets the numeric locale), so it lives in the factory, not at import.
- **The player renders in-scene via the libmpv render API, not `wid` embedding** — `wid` is dead on Wayland. `MpvVideoItem` (a `QQuickFramebufferObject` in `presentation/video/`) pulls the opaque mpv handle through the `MediaPlayer.render_handle()` port method; the mpv render context must be created on the Qt render thread (inside `createFramebufferObject`), and its `update_cb` fires on mpv's thread — hop to the GUI thread before calling `update()`.
- **The scene-graph backend is per-platform, and the video item follows it — see `infrastructure/graphics.py`.** **Windows** forces the OpenGL RHI for mpv (the only one `MpvVideoItem`'s FBO can render into); the native engine runs on Vulkan there instead, as on Linux, once `gv_native_vk_gpu()` finds a GPU, else on D3D11 through its readback path (`windows_native_graphics`; `GRAVITAS_GRAPHICS=d3d11|opengl` picks readback). **macOS defaults to Metal**, because Qt Quick refuses its threaded render loop on macOS with OpenGL — forcing `QSG_RENDER_LOOP=threaded` crashes in `-[NSOpenGLContext setView:]` on the render thread — so OpenGL there means the **basic** single-threaded loop, with animations, QML incubation, Python and texture uploads all on one thread; tab switches hitch where Linux/Windows stay smooth. libmpv's render API only speaks OpenGL, so macOS gets one of two other items under the same QML name `MpvVideo`: `MpvMetalVideoItem` when the native bridge (`native/macos/`, built by `scripts/build_video_bridge.py`) is present and matches the running Qt, else `MpvSwVideoItem`, which renders through libmpv's **software** API (~3.6 ms/frame at 1080p, ~6.8 ms at 4K on an M2) and takes `hwdec=auto-copy`. `GRAVITAS_GRAPHICS=opengl` restores the zero-copy OpenGL player on macOS. **Linux defaults to Vulkan** with `MpvVulkanVideoItem`, which keeps video zero-copy through the `native/linux/` bridge: mpv renders through OpenGL into an exportable `VkImage` that Qt's own Vulkan device samples (opaque-FD external memory, an EGL context matched to the Vulkan GPU by device UUID, and shared semaphores ordering GL against Qt's sampler). `GRAVITAS_GRAPHICS=opengl` forces the previous path back, and is the first thing to try if a driver misbehaves. The variable is ignored on Windows.
- **Nothing commits to Vulkan without asking the driver first — `gv_video_bridge_vk_probe()`.** Advertised extensions lie: Mesa's llvmpipe offers all four external-object extensions and then fails every imported allocation. Worse, the failure mode that actually bit here returned `VK_SUCCESS` and `GL_NO_ERROR` and delivered zeros, so checking return codes is not enough — the probe writes through GL and reads back through Vulkan to confirm the bytes cross. It runs **at 1920×1080, and the size is load-bearing**: with the dedicated-allocation bug deliberately reintroduced, a 64×64 surface round-trips perfectly and the probe passes, because small images never exercise the tiling and compression layouts the two APIs must agree on. It runs before `setGraphicsApi`, on its own throwaway instance and device, because that is the last moment OpenGL is still reachable.
- **The bridge finds libmpv through `/proc/self/maps`, not by soname.** python-mpv loads libmpv through ctypes (`RTLD_LOCAL`), so its symbols never reach the global namespace and the bridge has to re-open the same image by name — and in a bundle the name is whatever the *build* distro used: ubuntu-22.04 ships `libmpv.so.1`, Fedora `libmpv.so.2`, in a directory no search path names with `LD_LIBRARY_PATH` unset. That combination shipped a Flatpak where every layer reported success (`bridge loaded`, `renders zero-copy on Vulkan`) and video never appeared, because `resolve()` came up empty and mpv answered `No render context set`. Nothing calls the bridge without a live mpv handle, so the image is always already mapped: reading its path out of `/proc/self/maps` is a fact, and the soname list is only a fallback. Note that `dlopen(name, RTLD_NOLOAD)` *does* match a `DT_SONAME` on a library opened by absolute path — so a copy carrying the host's soname will hide this bug from a local test.
- **`GRAVITAS_HDR=hdr10|scrgb` is real plumbing behind an unsettled question.** It rides on the Linux Vulkan opt-in and names one chain end to end — surface format, the swapchain Qt requests (through a `_qt_sg_hdr_format` property on the window, which `QSGRhiSupport` reads when `QSG_RHI_HDR` is unset), and the transfer curve mpv renders with. Qt Quick *does* hand out an HDR10 swapchain on KWin/Wayland/Vulkan, so the once-recorded "Qt Quick is SDR-only" blocker is false. What is **not** established is which chain is colorimetrically correct: if Qt re-applies a transfer curve to an imported texture, one of the two is double-encoded. Both are off by default until someone checks a specular highlight against the player's own white UI text on an HDR display — real HDR highlights go far past SDR white. Do not promote either to a default on the strength of "looks fine".
- **Both native bridges are C++20, and their `Surface` is move-only on purpose.** Destruction stays explicit (`destroy_surface` / `releaseSurface`) because freeing a GPU object needs the right context current on Qt's *render* thread, and a destructor fires wherever the object happens to die — a `std::vector` reallocation would free on whatever thread pushed. What the type system does enforce is single ownership: retiring a surface is a `std::move`, so the old "copy the handles across, then blank the original by hand" idiom can no longer be got half-right. The same reasoning is why `create()` holds the bridge in a `unique_ptr` until every fallible step has passed, and why mpv's update callback checks a `shared_ptr<atomic<bool>>` liveness flag rather than reading `torn` off a bridge `destroy()` may already have freed.
- **Sharing a `VkImage` with OpenGL means agreeing on more than the format.** The Vulkan allocation is dedicated (`VkMemoryDedicatedAllocateInfo`), so the GL import *must* set `GL_DEDICATED_MEMORY_OBJECT_EXT` before `glImportMemoryFdEXT` — otherwise GL lays the image out for a suballocatable heap, the two APIs disagree about the same bytes, and GL's writes read back as zeros. That cost a day: it is format-independent, ring-size-independent, and invisible to Vulkan synchronisation validation because the fault is GL-side. Equally, `glSignalSemaphoreEXT` **releases** the texture out of GL along with its layout transition, and its contents stay undefined until a matching `glWaitSemaphoreEXT` **acquires** it back naming that layout — both halves are required, every frame. When something here renders wrong rather than crashing, substitute rather than theorise: clear the surface to a flat colour, skip mpv entirely, recolour the QML backdrop behind `MpvVideo`. Each of those isolates one layer in a single run.
- **The macOS video bridge is where Qt, mpv, Metal and OpenGL meet, and every rule in it was learned from a crash.** mpv renders through OpenGL into an IOSurface; Metal samples the same surface on Qt's own device; the scene graph draws it. `createTextureFromRhiTexture` **takes ownership** of the `QRhiTexture`; `QRhiTexture::createFrom` does **not retain** the `MTLTexture`; Qt's batch renderer keeps using a `QSGTexture` for an unbounded number of frames after its node is gone, so nothing may be freed at `sceneGraphAboutToStop` (nodes still exist there — that crashed the first fullscreen toggle). mpv's render context lives in C++ **because it cannot live in Python**: freeing it belongs on the render thread, Qt announces that through render-thread signals, and a Python slot there must take the GIL while the GUI thread holds it waiting for the render thread — a deadlock, sampled. A macOS fullscreen toggle stops the scene graph and emits neither `sceneGraphInitialized` nor `sceneGraphInvalidated`, so no "stopped" latch can be cleared reliably; don't add one. PySide6 is pinned to an exact patch release for this — QRhi has no binary compatibility guarantee, and the loader refuses a bridge built against a different Qt rather than crashing on a frame.
- **The stream proxy is on by default, and everything else must still work without it.** It is the default (`PersistedSettings.parallel_streaming`) because it measured ~2s faster to the first frame (see "Time to first frame" below), but the user can turn it off, and it steps out of the path by itself when it cannot help: a host the proxy thread cannot reach costs a probe before the 302 hands playback back to mpv. So nothing outside it may assume it is in the path — not the back-buffer sizing, not the connection estimate, not the source ranking. The choice is persisted under `stream_accelerator`, not the old `parallel_streaming` key: settings files are written whole, so an old `false` could not tell a choice from the old default, and is read as unset.
- **Time to first frame is logged, and each phase of it has an owner.** `MpvPlayer` logs `first frame N ms after load (file open at X ms, then Y ms buffering and decoding)` for every file (`file-loaded`, then the first `playback-restart`). Measured on a real AIOStreams→TorBox setup: the addon's playback URL is a signing endpoint whose redirect took **1330 ms** (a debrid lookup) plus ~400–800 ms per fresh TLS connection to the CDN. Four things act on that. `LinkWarmup` resolves the **top** row's redirect while the list is read (one per list: each resolve is a debrid API call), and the player `take`s it once, falling back to the addon URL first if it fails; `_current_url` stays the addon's URL so a reconnect an hour in gets a fresh link. `cache-pause-wait` starts each file at 1s and goes back to 4s at the first frame -- mpv uses one option for the initial wait and for stalls, and 4s before the first frame is ~12 MB of pure delay. The stream proxy, when on, cut the open phase from 3.3–4.0s to ~1.6s in the same measurements: throughput was equal (192 vs 205 Mbps, TorBox does not cap a connection here), but opening an MKV is several sequential range requests, each a fresh TLS handshake straight from mpv and a cache hit or pooled connection through the proxy. And a host that accepts the connection and never answers is caught by `PlayerController`'s 15s **open watchdog** -- `network-timeout` alone (10s) still let ffmpeg's reconnect retry a silent host for 65s, measured against a local server, where mpv's default would have been minutes.
- **mpv reads one HTTP connection, and no option changes that.** ffmpeg's HTTP client opens a single connection and reads it front to back, so a host that caps what *one* connection may do caps playback whatever the line can carry. That is how most debrid services shape traffic, and from inside mpv it is indistinguishable from a slow link. `infrastructure/network/segmented_proxy.py` puts the parallelism in front of mpv instead: a loopback HTTP server mpv plays from, which answers one range request with `CONNECTIONS` ranged requests against the real host and writes the blocks out in order. Three rules make it safe to leave on. It never guesses: a host that does not answer 206 with a `Content-Range` naming the total gets one plain connection and a straight copy, which is exactly what mpv would have done. `local_url()` is **synchronous, does no I/O and never raises** — that is what keeps `PlayerController.play()` a plain call, and a proxy that cannot help hands the URL straight back (non-http included, so `ytId` streams stay on mpv's own `ytdl_hook` path). And a seek is a new connection with a new `Range`, so the handler cancels its workers on the way out. One consequence to remember: with a proxy in the path **mpv's `cache-speed` measures loopback**, so while a stream is proxied `PlayerController._sample_speed` reads **only** `StreamAccelerator.upstream_bytes_per_s()`, and a 0.0 from it is no sample -- never a cue to ask mpv. That fallback once recorded the proxy's disk-cache read speed as the line (843 Mbps on a 260 Mbps connection), and the high-water estimate believed it. mpv's own reading is used only when the accelerator handed the URL straight back.
- **A proxy handler that will not die takes the next playback down with it.** mpv ends a connection by closing it, and every seek does. On macOS a `drain()` to a peer that has closed does not raise until it sends an RST, so the writer parked inside one, its workers parked on the memory semaphore holding their upstream connections, and with `max_connections` sized for one stream the *next* playback starved on the pool: 18s to first frame, then a stall at 0:86, then a screenful of "Task was destroyed but it is pending" on quit. Three things answer it, and all three are load-bearing. The writer runs as a task **raced against a watcher on the client socket** (`asyncio.wait(..., FIRST_COMPLETED)`), so the close is noticed by the side that cannot block. Teardown is `asyncio.wait(..., timeout=_CLEANUP_TIMEOUT_S)`, **not `gather`** — a bare `gather` over the just-cancelled tasks was itself observed to hang, and the handler must return whatever happens, because a handler that never returns is the leak. And a `stopping` flag makes any straggler finish the block in its hand and stop rather than read on down the file. `SegmentedStreamProxy` tracks its live handlers for exactly this, `shutdown()` is the synchronous form wired to `aboutToQuit`, and the regression test asserts `_handlers == set()` directly rather than inferring it from a later request succeeding — with a roomy pool a leak takes several playbacks to show as a stall.
- **A proxy that cannot serve answers 302, it does not close.** mpv's ffmpeg retry loop never gives up, so a local URL that can never work is an endless spinner, not an error — "giving up" on the *next* `play()` is far too late when there is no next `play()`. So when a request fails before a single byte is sent (`_ResponseState.started` is the guard), the handler replies **302 to the upstream URL** and ffmpeg follows it in the same request: playback continues directly, and nothing above ever learns there was a problem. A proxy that fails has to fail *out of the path*, not in it. `_MAX_ENTRY_FAILURES` retiring the stream is only an optimization on top — it saves the next connection a round trip, it is not the recovery. **The one exception is a refused connect** (`_unreachable_host`: `httpx.ConnectError`/`ConnectTimeout` only, never a read that died mid-response): a 302 is advice to dial a URL, and the proxy has just proved from this machine — same resolver, same routes — that mpv cannot dial it either. Redirecting there buys nothing but ffmpeg's retry ladder before the same answer arrives ~10s later, and a debrid signer points every source of a title at one CDN node, so that is paid once per source in the fallback queue. Those get **502**, which mpv reports as a load failure at once (ffmpeg does not retry an HTTP status unless `reconnect_on_http_error` says so) and `_try_next_source` walks immediately. The refusal is also the only place the *host* is known — every stream URL is a signing endpoint that redirects, so the player only ever sees the addon's domain — so it is kept on `last_failure()` for `PlayerController._unreachable_message()` to show. `_describe_unreachable` resolves the host on that path to tell a refused node from one the machine's own resolver has sinkholed: a blocklist answers `0.0.0.0` and the connect is then refused instantly, which is byte-for-byte what a dead CDN node looks like and wants the opposite response.
- **A failed upstream probe is not a fact about the host, and a broken proxy must stand aside.** `_probe` originally answered a refused or timed-out request by recording `ranged = False` — the same value it uses for "the host answered and does not serve ranges". One bad moment therefore made the stream unsplittable for good: every later connection went straight to the passthrough that had just failed, mpv reported `Error reading HTTP response: End of file` instantly on each retry, and nothing recovered. A transient failure now raises `_ProbeFailed`, which serves that one request the plain way and leaves the next connection to probe again. A **`429` answer** is the same kind of fact about a moment, and it was the one still cached: a `429` is not a `206`, so a throttled account's probe recorded "no ranges" and the passthrough handed mpv the `429` on every connection. `_probe_request` waits a rate limit out on the block fetcher's own schedule (`_PROBE_RATE_LIMIT_ATTEMPTS`, about 12s) and raises `_ProbeFailed` if it outlasts that. Behind that, `_MAX_ENTRY_FAILURES` handler failures on one stream put its upstream URL in `_broken`, and `local_url` then hands that URL straight back — so the next `play()` or stall-recovery reconnect reads it directly through mpv. "No worse than mpv on its own" has to hold when this module is the thing that is broken. One more rule that follows from the same incident: `_handle` logs its exception at **warning with a traceback**, never debug. mpv's report names the symptom and the proxy is the only place the cause exists.
- **The proxy caches on an aligned chunk grid, and backfills behind a resume point.** Alignment is the whole reason the grid exists: mpv answers a *seek* by opening a new connection to the same URL, so a chunk fetched for one position has to be reusable at another, and a range starting anywhere inside a chunk has to hit the same entry. With that, going back and then forward again costs no network at all. The cache is per-stream (it dies with the registration, so a debrid URL's bytes do not outlive its playback), bounded, and evicts **furthest-from-playhead** — not LRU — because backwards and forwards are equally likely and the bytes under the playhead are the ones worth keeping. Separately, one worker walks *backwards* from the starting offset: resuming at 3:51 means nothing before 3:51 was ever downloaded, and no cache helps with bytes nobody fetched. It runs **only while the writer is parked in `drain()`**, which is mpv refusing bytes because its own demuxer cache is full — that is exactly and only when there is spare bandwidth, and it yields the instant mpv wants something again. With a `cache_dir` (which `main.py` always passes) the cache is **on disk**, one file per chunk, `DISK_CACHE_MAX_BYTES` split 2:1 ahead:behind the chunk mpv is reading, each side evicted against its own share; the proxy then reads ahead into that whole ahead-share rather than `READAHEAD_CHUNKS`. The directory is wiped when the proxy thread starts (a crashed session's debrid bytes), per stream when the next `local_url` retires it, and entirely on shutdown; one that cannot be made drops the proxy back to the in-memory cache, never out of the path.
- **The stream proxy runs on its own thread, and that is not an implementation detail.** qasync makes the app's asyncio loop *be* Qt's event loop, so any coroutine scheduled on it runs on the **GUI thread** — the one driving QML animation and scene-graph sync. Serving 25 Mbps from there means TLS decryption, HTTP body assembly and a multi-megabyte socket write arriving in bursts of roughly one per second, and that lands as a visible hitch in the video about once a second. ffmpeg never did any of this on the GUI thread, because ffmpeg is not Python. `SegmentedStreamProxy` therefore owns a daemon thread with its own loop; the only thing that crosses is `local_url()` (its dict is lock-guarded) and the rate meter's reader. Blocks are also written to mpv in `_WRITE_SLICE_BYTES` slices rather than one 4 MiB call, so the same bytes move as a trickle the loop interleaves instead of a burst.
- **429 is the host asking for fewer readers, not a failed block.** A debrid CDN that shapes an account answers the seventh concurrent range request with `429`, and the first version spent the block's retry budget on it and then ended mpv's connection — `Stream ends prematurely at 373293056, should be 11587442928`, mid-episode, on a stream that was playing fine. Rate limiting therefore has its own budget (`_RATE_LIMIT_ATTEMPTS`, separate from `_BLOCK_ATTEMPTS`) and its own answer: `_slow_down()` drops `_Entry.parallel` by one, workers above the new limit return at the top of their loop, and the retry waits `max(Retry-After, backoff step)` — a floor, because a host answering `Retry-After: 0` means "not now", and honouring the 0 literally burns the whole budget inside a millisecond. Two details are load-bearing. The shrink is **debounced** (`_SHRINK_DEBOUNCE_S`): six workers over the limit all hear the same one limit, and without it one round trip takes the stream from six readers to one. And `parallel` lives on the **entry**, so it outlives the connection — mpv answers a seek by opening a new one, and starting that back at six re-earns the 429 every time. The floor is one reader, which is exactly what mpv would do on its own. What a host teaches outlives the stream too: `_host_limits` keeps the connection count it last accepted per host for `_HOST_LIMIT_TTL_S` (15 min), and a new stream -- a new debrid token, the next episode -- starts there instead of at `CONNECTIONS`, which re-earned the same 429s on every playback. `CONNECTIONS` itself is 4: TorBox refused 2 of 6 concurrent long requests on one file while one connection alone ran at 192 Mbps. And mpv's `network-timeout` is per load (`_PROXIED_NETWORK_TIMEOUT_S`, 60s, for a loopback URL): the proxy's 429 backoff legitimately runs past the 10s a direct URL gets, and cut off there mpv abandoned the proxy mid-backoff and reconnected into more 429s -- a stall that looked like "the player loads sometimes".
- **A teardown that awaits can itself be cancelled.** `_pump`'s cleanup asks its workers to stop and then awaits them, and when the app quits mid-stream the handler task is cancelled *while it is in there* — the grace `await` raises, the straggler `cancel()` calls never run, and the loop closes on seven live tasks: one `Task was destroyed but it is pending` each, at the exact moment the app is quitting. The cancellation therefore lives in a **nested `finally`**, because `cancel()` needs no await and so survives it, and `_serve_forever` sweeps whatever is still on the loop after the handlers are done. Any teardown here that ends with an `await` needs the same treatment.
- **Cancelling an httpx request mid-`connect_tcp` wedges httpcore's pool, and closing that pool then blocks.** This is the second bug with the same shape as the first, one layer down: teardown cancelled its workers, some were mid-connect, the slot stayed held, and `AsyncClient.aclose()` never returned — so the handler never reached `writer.close()`, mpv never saw EOF, and the request hung forever. Two rules keep it away. Teardown **asks before it cancels**: it sets `stopping`, releases the semaphore once per worker to wake whoever is parked on it, waits `_GRACE_TIMEOUT_S` for them to finish the request in hand, and cancels only what is still running. And each mpv connection gets **its own `AsyncClient`**, closed under a `wait_for`, so a slot that does leak dies with the connection that leaked it instead of accumulating across seeks until nothing can connect. A shared client plus cancellation is what turned a seek into a stall.
- **Requests go to the URL the redirects resolved to, and cover runs of chunks, not one chunk each.** An addon stream URL is a signing endpoint that 302s to a CDN; `follow_redirects` on every request meant a round trip through the slowest hop each time, so the probe's resolved URL is stored on the entry and used first, with the original as the retry fallback (a CDN URL can expire). The cache grid is 1 MiB chunks, but a worker claims a **run** of up to `RUN_CHUNKS` (8) consecutive chunks and streams it in one ranged request, handing each chunk to the cache the moment its last byte arrives -- so the first chunk of a run is no slower than a lone chunk, and mpv's header/index/seek reads at open still cost little. One request per chunk was ~20 requests/second at start-up on a fast line, and a TorBox CDN answered that with 429 on half of them (measured: sequential requests fine, 15 of 30 refused in six-way bursts); runs brought the peak under 8/s. Workers also wait for room for a whole run while the read-ahead window is comfortably full (`ahead > whole_run`), or steady play claims each freed slot singly and is back to one request per chunk (4-6/s measured; ~1/s with the wait). Three safety rules came with runs: read-ahead is capped at what the cache can hold (a run landing faster than mpv reads would evict chunks the writer has not sent); a writer waiting on a chunk that is neither cached nor in flight rewinds the cursor to it rather than waiting forever; and the body iterator is closed with `contextlib.aclosing`, plus `loop.shutdown_asyncgens()` when the proxy thread ends -- a stream cut off at quit otherwise left httpx/httpcore generators to be finalized after their loop was gone.
- **Tuning options are applied one at a time after construction, never in `mpv.MPV(...)`.** The constructor applies its whole keyword set in one go, so a single name this libmpv does not have takes down playback entirely — `'mpv option does not exist', -5, ... b'cache-dir'`, and nothing plays at all. mpv renamed that one to `demuxer-cache-dir` in 0.41, and `_CACHE_DIR_OPTIONS` now tries both. The rule is the general one: no piece of tuning is worth a player that will not start, so `_set_option()` sets each through the options namespace, reports whether the build has it, and an unknown option costs exactly itself. It also means the *sizes* can follow what actually took — `_apply_cache_options` only raises the limits to `_DISK_*` once `cache-on-disk` is confirmed applied, because a gigabyte of back-buffer is reasonable on a filesystem and is not reasonable in RAM.
- **The demuxer cache lives on disk, and that is what makes seeking feel like a player — except behind the proxy, where the proxy's disk is the cache.** A direct URL gets `_DISK_MAX_BYTES`/`_DISK_MAX_BACK_BYTES` on disk, so anywhere already watched is instant. Played through a proxy that `holds_stream_cache()`, `PlayerController` passes `play(upstream_cached=True)` and mpv drops to `_UPSTREAM_CACHED_OPTIONS` — in memory, 192/96 MiB — because two gigabyte caches of the same stream is the machine paying twice, and mpv's copy cannot answer a track switch anyway (it holds packets of *selected* streams only). Demuxer options are read when a file opens, so this is set per load, and `MpvPlayer` reads the factory's values back at construction so the next direct load restores them rather than inheriting the small ones.
- **Changing `aid` is a network operation, so the audio tracks are all kept hot in a filter graph.** mpv drops the packets of every stream it is not playing, so selecting another audio track sends the demuxer back to the current position to re-read it: a fresh HTTP request, the read-ahead thrown away and a re-buffer before playback resumes. Measured against a host serving at 5x the file's bitrate that is 2.3s of frozen picture, and 9.6s at 1.4x — with the whole stretch already on disk in mpv's own cache, which does not help because the cache holds *packets of selected streams*, not bytes. `--lavfi-complex` is the way out: a graph selects every track it names, so `_audio_graph()` routes the chosen track to `[ao]` and sinks the rest with `anullsink`, and a switch is then a graph swap over packets mpv already has — no request, no re-buffer, zero stall measured (and the AO's tone really does change, checked at 440Hz/880Hz, with 5.1 AC3 ↔ stereo AAC reconfiguring the output correctly). Three rules hold it up. The graph goes in **while the file is young** (`prepare_track_switching()`, on the first track list), because installing it selects new streams and therefore pays exactly the re-read it exists to avoid — 0.06s after `play()` in practice, and free. It is installed **from the GUI thread**, never from mpv's track-list observer: that callback runs on the thread mpv delivers events on, and this sets a property, so `PlayerController` hops through the private `_tracksReady` signal the way `_streamEnded` does. And every failure falls back to plain `aid` switching — a libmpv that will not build the graph, or a file with more than `_MAX_HOT_AUDIO_TRACKS` audio tracks. That cap is the price side: every track in the graph is decoded for as long as the file plays (8 AC3 5.1 tracks measured at 1.06s CPU per 20s of playback, against 0.15s for one), and their packets share the demuxer cache's byte budget, so read-ahead measured in seconds shrinks by their share. Bandwidth is untouched — they all come out of the same byte stream. Installing the graph also **silences the selected embedded subtitle track** for the rest of the file: `sid` still names it, `sub-text` stays empty, and a seek does not help (measured on South Park S6E1, six AC3 tracks + SubRip, resumed or not). Selecting it again does, so `prepare_track_switching` sets `sid=no` and back straight after. That re-read cost 1.5-2s of first-frame time on a direct link (7.5-8.0s against 6.0-6.4s). Note `aid` reads back as `no` once a graph is installed, so `current_audio_track()` answers from the id the graph was built with. A **sparse track** is the graph's other failure mode: every track in it is selected, so one with a gap (a commentary, a partial dub) holds the others in the demuxer queues while mpv reads ahead for its next packet -- `Too many packets in the demuxer packet queues`, then `eof state changed on aidN` storms, and in a real session over a throttled link an audio underrun and a frozen picture (South Park S6E1, six tracks, `audio/6: 0 packets`). mpv reports the overflow in its log, so `_mpv_log_handler` hands it to the player, which takes the graph down for the rest of that file (on a thread of its own: the log fires on mpv's event thread) and puts the playing track back on plain `aid`. Reproduced locally only as far as the overflow and the eof storm; playback of a local file survives them.
- **Subtitles have no such escape, so "Off" hides the track instead of dropping it.** `sid=no` frees the track's packets, and turning subtitles back on then costs the same refresh seek as an audio switch (2.2s measured at 5x). `sub-visibility=no` keeps it selected and costs nothing to undo, so off/on is instant and `current_subtitle_track()` reports None while hidden. **Addon subtitles are the way out of it**: the protocol's `subtitles` resource (`AddonRepository.subtitles`, AIOStreams and OpenSubtitles serve it) names whole files, `MediaPlayer.add_subtitle` loads one with `sub-add`, mpv reads it entire, and switching to, from and between them costs nothing. `sub-add` blocks while it downloads (1.3s measured), so it runs on a worker thread; a reconnect drops added files, so `PlayerController` re-adds them. They are listed after the file's own tracks (ids from `ONLINE_SUBTITLE_ID` until loaded), and one is loaded by itself when a language is preferred and the file has no track in it -- after `choose_fallback_subtitle`, which takes an *untagged* track whose title names the language (mpv matches tags only, and many files put "English" in the title instead). **Never judge the empty track list**: mpv reports one when the callback registers and again as each new file starts loading, before the real list arrives -- settling on it read every file as subtitle-less and loaded an out-of-sync addon file over the file's own English track. Nor judge the *selection*: mpv lists a file's tracks before it chooses among them (the `on_preloaded` hook sits between the two), so "nothing selected" can mean "not chosen yet". `has_preferred_subtitle` reads the language off the track list instead (a forced-only track does not count), and `choose_fallback_subtitle` stands aside whenever a track is tagged with the language, since mpv will take it. An addon's file is timed to its uploader's release, so `_online_in` ranks files sharing the playing source's release words (group, resolution, source, and the file name from `behaviorHints.filename`) first, counting only words at most half the offered files carry -- a show's name is on all of them and says nothing. That matters more than timing: one aggregator's "S06E01" list mixed two different episodes (a DVD-order and an air-order release), streams and subtitle files alike, and a subtitle for the other episode reads as drift that no delay fixes, and G/H shift `sub-delay` by 0.1s for the rest, reset per new file. Switching between two *different* subtitle tracks still pays the seek, and nothing in mpv avoids it: `--lavfi-complex` has no subtitle labels, `sid` + `secondary-sid` is two slots and swapping them deselects one (which re-reads anyway), and displaying the secondary slot would strip ASS styling. Through the disk-backed proxy it is **free**: the refresh seek re-reads bytes the proxy is holding on local disk. Measured on one 4K TorBox file, same switches: direct 2.0–2.6s frozen behind the spinner every time, proxied 0.00s. That is why the proxy's cache is on disk at all — in memory it had evicted the bytes around the playhead long before a switch asked for them.
- **Preferred languages are mpv's own `alang`/`slang`, and a hand-picked track would silently outrank them.** mpv chooses tracks by language as it opens the file, so a preference costs no switch and no refresh seek. `domain/languages.py` hands it every spelling a muxer uses (`de,ger,deu`), because only newer builds match across ISO 639 variants. Two rules make it hold. Setting `aid`/`sid` at runtime writes the *option*, and mpv carries that id into the next file, where it beats `alang` (measured on 0.41: `aid=1` in one file played track 1 in the next with `alang=de`), so `MpvPlayer.play()` resets both to `auto` whenever `set_track_languages` came first. And the preference is applied **per new file only**: `PlayerController.play()` calls it, `_reconnect_now()` does not, and a `play()` with no call before it is a reload that keeps the viewer's tracks. A switch made through the hot-audio graph never writes `aid` at all, so on a reload `MpvPlayer` restores the graph's selection itself. Without that, a reconnect opened on the preferred or default track. Subtitles "Off" hides rather than deselects, for the reason in the next rule. The flags are SVGs shipped under `qml/flags/`, fetched by `scripts/vendor_flags.py` for exactly the countries the catalog names (re-run it after adding a language; a test fails on a missing one). They were emoji first, and emoji depend on a system colour-emoji font: the Flatpak runtime has none and Windows has no flag glyphs, so the menu showed blank space.
- **A source that never opens is answered with the next source, not with an error.** A debrid CDN node that refuses the connection takes *every* source pointing at it down with it — the addon signs a whole title's streams to one node — and that says nothing about the title. So `DetailController.sourceQueue(row)` hands the rows below the clicked one to `PlayerController.setSourceQueue()` at click time, and `_try_next_source()` walks them. It fires **immediately** on the first never-opened end-of-stream rather than after `MAX_OPEN_ATTEMPTS`: ffmpeg has already retried that URL several times internally by then, so the source has had its chances and every further second is spinner. `SOURCE_QUEUE_LIMIT` caps it **after** filtering out entries with nothing playable, not before — slicing first let a junk row at the top cost a real fallback at the bottom. `stop()` drops the queue, because leaving the player is not a request to keep trying sources.
- **A film or episode shorter than a minute is a host's error clip, not the title.** A slate served as video (the "Wrong IP" one above) opens, plays a second or so, often with no duration, and ends -- which read as a dropped connection, and stall recovery reloaded the same link forever. `PlayerController._served_slate` (media identity set, the source opened, duration under `SLATE_MAX_S`) moves to the next source instead, or says so when there is none, and `_record` never saves such a clip's position: it would overwrite the viewer's resume point. Trailers carry no media identity and are exempt.
- **"Never opened" and "dropped mid-episode" look alike and want opposite patience.** They arrive by different routes — a drop as `eof-reached`, a source that never opened as the `end-file` error above — and both land in `_on_stream_ended`. A connection that dropped deserves `MAX_RECONNECT_ATTEMPTS` over ten minutes, because the network usually comes back. A source whose host refuses the connection — a dead CDN node behind a debrid signer, which is common and transient per node — never comes back on that URL, and the viewer is sitting in front of a list of other sources that probably work; ten minutes of retrying is a spinner, not a recovery. `_never_opened` (no duration *and* no position, so nothing was ever decoded) selects `MAX_OPEN_ATTEMPTS` instead and ends with a message naming what to do about it. Note ffmpeg retries internally forever on its own (`Will reconnect at 0 in N second(s)`), so without this the spinner really is unbounded.
- **A source that never opens produces no end-of-file at all, so it needs its own signal.** `eof-reached` says the file that was playing has run out; a file that never started playing never sets it. mpv answers a URL it could not open with an `end-file` event whose reason is `MPV_END_FILE_REASON_ERROR` (4) and then goes idle, silently as far as every property observer is concerned — so with only the `eof-reached` observer wired, a refused host was an endless spinner: `_on_stream_ended` never ran, the source queue was never walked, and no error was ever shown. That is the everyday failure of a debrid CDN node (`nexus-156.nord.tb-cdn.st` refusing every connection while the addon kept signing to it), and it looked like a launch-mode bug because the terminal run happened to draw a live node. `MediaPlayer.set_load_failed_callback` registers on the event stream instead, fires only on reason 4 — every other reason is an ordinary end (`stop()` aborts, the next source replaces, the file finishes), and reporting those would restart playback on the way out of the player — and hops to the GUI thread through `PlayerController._loadFailed` into the same `_on_stream_ended`, which already tells "never opened" from "dropped mid-episode". The reason is read out of whatever the binding hands over (an `MpvEvent` struct on recent python-mpv, a dict on older ones) and an unreadable event reports nothing: a false positive abandons a source that is playing.
- **A dropped connection reaches mpv as end-of-file, not as an error.** ffmpeg's HTTP reader turns a read that fails while the network is down into EOF, so mpv concludes the file finished and — under `keep-open=yes` — holds the last frame paused. `paused-for-cache` never goes true, so the loading overlay never shows, and nothing retries when the connection comes back: playback simply stops mid-episode. Two layers answer it. `_STREAM_LAVF_OPTIONS` passes `reconnect_on_network_error=1` through `--stream-lavf-o`, which is what makes ffmpeg retry a *failed socket* rather than only a connection the server closed cleanly — plain `reconnect`, which mpv sets itself, does not cover it. Its sibling `reconnect_streamed=1` was there too and had to go: it breaks every ytdl-resolved stream, because yt-dlp hands mpv an EDL naming byte ranges into googlevideo and a reconnect that reissues from zero contradicts them, which ffmpeg reports as `End of file` and retries forever — a trailer spins and never plays. Note mpv splits that option on commas, so no value in it may contain one (which rules out `reconnect_on_http_error=4xx,5xx`). Behind that, `PlayerController`'s stall recovery hangs off the `eof-reached` observer (`MpvPlayer.set_stream_ended_callback`): an end-of-file more than `END_OF_STREAM_SLACK` short of the duration is a drop, and it reloads the same URL — with the stream's proxy headers — at the position playback froze at, backing off to 30s and giving up after 20 attempts. It waits for the play button if the user had paused, and disarms on `stop()`, which itself ends the stream and would otherwise reload the episode. A reload counts as recovered only if it lands within `RECOVERY_JUMP_S` of the stall point: one whose seeks were all refused could not read the file's index and came up at the last second of the episode, which the autosave then recorded as watched. While reconnecting, `_record` saves the stall position, and an end of file is another failed attempt rather than the episode finishing. Separately, "never opened" is `no duration and (no position or no opened report since play())`: for a resumed episode the position is `start` before a byte is read, and that used to retry a dead source as a dropped connection instead of moving to the next one.
- **`cache-speed` is a floor on the connection, never its capacity.** The opt-in source sort (`sort_by_connection`, off by default) ranks Sources by what the link can sustain, and its only measurement is mpv's own read speed sampled on the 5s autosave tick. Once the demuxer cache is full mpv reads at roughly the file's bitrate, so most samples measure the *file*: a mean, a median, or any percentile over them answers "8 Mbps" on a 500 Mbps line, because the fast stretches (start-up fill, post-seek, post-stall) are a small minority of the samples. `application/connection_speed.py` therefore takes a high-water mark with the single highest sample discarded, and errs low on purpose — underestimating puts a smaller file at the top, and a smaller file plays. Samples are bucketed by Qt's transport medium and the running session outranks stored history at 5 samples, so a laptop moved from ethernet to hotel wifi corrects inside one playback instead of averaging the two networks together. Ranking is by the picture the panel receives, not the number in the label: `infrastructure/display.py` reports the tallest screen in *physical* pixels (Qt reports logical — a 2x Retina panel says 900, and capping at 900p would demote everything good), and a source taller than that ranks at the panel's height, below a native source of the same height that delivers the identical picture for a third of the bandwidth. An unknown screen (0) caps nothing. A cold link is measured once by `infrastructure/network/probe.py` against the top stream's own host (3 MiB, 2s) — never a speed-test service — and bytes past the requested range are not counted, since a host that ignores `Range` would otherwise report a rate nothing asked for.
- **Dolby Vision profile 5 plays magenta, and no backend here can fix it.** `render.h` offers `MPV_RENDER_API_TYPE_OPENGL` and `..._SW` only, and `vo=libmpv` is the old `vo_gpu` renderer — libplacebo (`vo=gpu-next`), the only thing that converts profile 5's IPT-C2 colour, is not reachable through the render API at all. So a profile 5 file renders wrong on OpenGL, Metal, Vulkan and software alike; it is not a macOS bug, not the missing `libgravitas_video_bridge.dylib`, and not worth re-debugging as one. Profile 8 carries an HDR10 base layer and is fine, which is why it looks intermittent, and why the addon's `DV` label cannot be used to predict it — `MpvPlayer.video_dolby_vision_profile()` reads `track-list`'s `dolby-vision-profile` off the *selected* video track instead, and `PlayerController` warns the viewer once per playback.
- **Inside a tier, bitrate stops counting once the panel cannot show it.** The first version of the recommender ranked by raw bitrate within a tier, and on an all-4K list on a laptop panel that picks the 25.3 Mbps file over the 14 Mbps one — both downscaled to the same 1440p picture, one of them three times more likely to buffer. `useful_mbps()` clamps a source's bitrate at `NOMINAL_MBPS[height_tier(tier)] * USEFUL_MULTIPLE`, and ties on the clamp are broken by the **lower** actual bitrate: enough, and no more. Note `height_tier()` rather than a direct `NOMINAL_MBPS` lookup — a tier is capped by the panel, and a real panel is whatever it is (a 14" MacBook reports 1964 physical pixels), so a raw lookup missed and silently fell back to the "unknown screen" rate, which is below 1440p's.
- **A "Recommended" mark is a claim, so it is only ever made out of evidence.** `application/recommendation.py` marks one source per *delivered* quality tier (the picture the panel shows, so on a 1080p laptop the 4K and 1080p rows are one tier, not two) and lifts the marked rows to the top under a section header; `MAX_PICKS` caps it at 3, because a list where a third of the rows are recommended has recommended nothing. Four inputs gate a pick, and each is a fact the app holds: the screen (`infrastructure/display.py`), the measured line (`ConnectionSpeed.estimate_kbps`, with `HEADROOM`, falling back to the tier's `NOMINAL_MBPS × UNMEASURED_CEILING` so an 80 Mbps remux is never recommended blind), the renderer (`compatibility.is_incompatible` — applied **even with `hide_incompatible` off**, since listing a broken source and recommending it are different things), and the decoder. With no evidence at all nothing is marked, and an unmarked list is the right output. Two consequences to keep in mind: the estimate now has a second consumer, so `ConnectionSpeed.needs_probe(wanted=...)` exists and the one-shot cold-start probe runs when *either* the sort or the marks are on — the marks are on by default, so a fresh install probes on its first Sources page. And because the marks are computed against the real screen/estimate while the sort still is not, `_render_streams` keeps `sort_height`/`kbps if sort_on` separate from the values it hands the recommender.
- **The decoder's capacity is learned from mpv, never guessed.** Core count says nothing about whether libmpv's ffmpeg has this codec's hwaccel, and `hwdec-current` reports that hardware decoding *engaged*, not that it kept up. `application/playback_capability.py` therefore files verdicts by `(codec family, height tier)` from mpv's own `frame-drop-count` + `decoder-frame-drop-count` (`MediaPlayer.decode_report()`), and a bucket it convicts is never recommended. Three rules keep it honest: a playback under `DECODE_OBSERVATION_MIN_S` files nothing (the drops while a seek settles are not a verdict), the denominator counts **autosave ticks**, not wall time, so an hour paused is not an hour of evidence, and `DECODE_STRAIN_DPM`/`DECODE_SMOOTH_DPM` are deliberately apart so a marginal machine does not flip its verdict every other episode. `play()` resets the counters because mpv's do too. The verdict rides `_persist_speed`'s single settings write rather than adding its own.
- **Hiding a source needs evidence, and a label is not evidence.** `hide_incompatible` (off by default) keeps sources the renderer cannot display out of the list — today that means Dolby Vision profile 5 only. The addon label cannot state the profile, and `DV` alone does not mean broken: `DV · HDR10` is profile 8.1, which carries an HDR10 base layer and renders correctly, while bare `DV` has no base layer to fall back to and is usually profile 5. So `application/compatibility.py` runs that shape as a *heuristic* and treats mpv's own `dolby-vision-profile` as *fact*: a release caught rendering as profile 5 is remembered by a normalised label signature (a debrid URL is single-use and cannot identify the release tomorrow), and a remembered verdict outranks the guess in both directions. Two rules keep the filter honest — `partition()` returns the list whole when *everything* would be hidden (a magenta picture beats an empty page), and every source list shows `N hidden` with a reveal, because a filter the user cannot see is one they cannot correct.
- **QML's `Image` never reaches Python.** Artwork is fetched by Qt's own network
  stack, so an httpx-based cache cannot see it. `cache/network_cache.py` installs a
  `QQmlNetworkAccessManagerFactory` (before any QML loads, and kept alive on the
  engine like the QML singletons) so `QNetworkDiskCache` caches posters honouring
  CDN cache headers. Addon JSON is separate: `AddonClient` caches it in-process
  per kind — manifest for the session, meta 24h, catalog 15m, **streams never**
  (links expire; `_get_json` defaults to uncached so a new endpoint is safe).
- **A stream list on screen before the addon answers is a placeholder, never an answer.**
  A stream aggregator (AIOStreams) holds its response for its whole scraper timeout —
  ~5s to first byte, measured — so nothing client-side can make a first visit fast.
  Three things hide it. `ResolveStream.prefetch()` starts the fetch before the click
  (movie open, series open on the likely episode, a 250ms dwell on an episode row), and
  a click joins the request in flight. A finished list answers again for `REUSE_S`
  (5 min) unless it was empty or an addon failed. And `AddonClient` writes every stream
  answer to disk, which `stored_streams()` reads back so a revisit shows rows at once (the
  title's meta has the same arrangement: `stored_meta()` stands in when the fresh fetch has
  not answered in `STORED_META_AFTER_S`, and a changed episode list is re-read without
  resetting the season on screen) —
  but `fetch_streams` still always goes to the network, `streamsLoading` stays true until
  it lands, and the fresh list replaces the stored one wholesale. The one exception: a
  fresh answer with nothing playable leaves the stored rows up, because an aggregator
  whose scrapers all timed out answers empty, and rows that may play beat an empty page.
  Stored links can be dead for an addon that hands out expiring URLs -- or alive and wrong:
  a signed link can be bound to the address that asked for it, and after the ISP moved the
  /64 an ElfHosted link served a "Wrong IP" *video* instead of the episode, which opens and
  plays and so fails nothing. So a stored row is **never played**: while `sourcesStored`, a
  click calls `pickWhenFresh(row)` and the page plays whatever `freshSourceReady` names --
  the same release's row in the fresh list (matched by label, as below), or the stored row
  itself when the fresh request failed or came back empty.
  Two more head starts ride the same machinery. A poster the pointer rests on for 350ms
  (and an episode row, after 250ms -- both are guesses, both capped) calls `DetailController.prefetchTitle`: the meta is warmed (`GetDetail` shares a running
  fetch with the click) and the sources are *guessed* through `ResolveStream.speculate`,
  which drops a guess outright while `MAX_SPECULATIVE` are in flight — every guess is an
  aggregator scrape plus debrid check, and a pointer crossing a row must not become a
  burst. And the player calls `prefetch_after` once per episode `NEARING_END_S` from its
  end, so the next episode's list is ready when the viewer goes back to it.
  A fresh list over a stored one is applied **in place** by `StreamListModel.set_streams`
  (remove/move/insert/update, never a reset, `QAbstractItemModelTester`-checked), and rows
  are matched by **label, never URL**: an aggregator re-mints every URL per request
  (0 of 93 shared between two identical requests, measured). Finally, "nothing playable"
  and "an addon did not answer" are different facts: the second raises
  `SourcesUnavailable` (a `NoStreams` subclass, so every "empty" path still holds) and the
  page offers a retry instead of claiming the title has no sources.
- **A long list belongs in a view, not a `Repeater` in a `Column`.** A Repeater is never lazy: every delegate is built in the frame the model resets, and every one stays alive. The movie page's inline Sources did that with 90–150 aggregator rows (~20 items each) and paid twice: 150–250ms of blocked GUI thread per reset, then — because `BackButton`'s frosted glass is a *live* `ShaderEffectSource` over the page, which re-renders its entire source subtree whenever any of it changes — a render-thread p95 of 29ms per frame while scrolling or hovering (57 fps on a 144Hz panel, RTX 2070, measured on the real display; offscreen showed no difference at all, so measure there). Detail.qml is therefore a `ListView` whose `header` is the metadata and whose delegates are the sources: 141 fps, render p95 2ms, frost kept. Anything inside the header that the page needs (the episode count) comes out through a `Binding`, since a header's ids are not visible outside it. Any new blur target should be checked the same way: its cost is the size of what it blurs, not of the button.
- **Source ranking runs on a worker thread, and must stay pure to stay there.** `DetailController._render_streams` snapshots everything it reads into `_RenderInputs` on the GUI thread (the screen height is a Qt query; the connection estimate, known-bad and strained sets are mutable), then runs `_rank_for_display` via `asyncio.to_thread` — 145 sources cost ~5ms (`recommend` 3.1, `rank_streams` 1.8), twice per open, against a 6.9ms frame at 144Hz. A result is applied only if `_render_seq` has not moved: every render and every `_clear_streams()` bumps it, so a ranking overtaken by the next title never paints over it. Anything added to the ranking must read its inputs from the snapshot, never from `self`.
- **Picture-in-picture on KDE/Wayland is KWin's job, and the size has to be held.** The window flags (`FramelessWindowHint | WindowStaysOnTopHint`) are the whole story on X11, Windows and macOS. Wayland has no stay-on-top protocol, and KWin also ignores a frameless flag set on a window that is already shown -- asked directly, it reported the tile `keepAbove=false noBorder=false`: a title bar on a 480px video that any window could cover. `infrastructure/desktop/kwin_window.py` therefore loads a KWin script over the session bus (`org.kde.KWin /Scripting`) for as long as PiP is on: it sets `keepAbove` and `noBorder` on this app's normal windows and on any opened later (`windowAdded` -- a flag change can recreate the surface). Windows are matched by **app id** (`resourceClass`, the desktop file name), not by pid: inside a Flatpak the app has its own pid namespace, so the pid it knows is not the one KWin sees, and the script found nothing to pin. The Flatpak also needs `--talk-name=org.kde.KWin`, or the sandbox cannot see the bus name at all. Leaving unloads it *before* the flags change back, then runs one that hands both back. **Script names are not unique across runs** -- inside the Flatpak the app is always pid 2 in its namespace -- and KWin answers `-1` to a load under a name that is still loaded, which a run killed without `aboutToQuit` leaves behind. That refused the Flatpak's restore script, so leaving PiP left the window frameless and on top. So every load unloads its name first, and `for_session` sweeps every script this install ever wrote (the names are its own files under `cache_dir()/kwin`). It is a no-op anywhere else; GNOME/Wayland has no equivalent and the tile can be covered there. Separately, `Main.qml`'s `_requestSize` holds a requested size for 600ms: every flag or frame change is answered by a compositor configure carrying the size from *before*, which lands after the request and wins -- measured, leaving PiP restored 1280x800 and was back at 480x270 within 100ms, and removing the frame on entry produced 1472x828. Anything the platform sets inside that window is answered with the size asked for. And the compositor can end PiP by itself: KWin's maximize on the tile arrives only as `visibility` turning `Maximized` (measured: 1920x1036, still `noBorder=true keepAbove=true`, because the float script is still loaded). `Main.qml` treats that as leaving PiP into that state, without asking for the old size (the hold would pull the window out of the maximize), and asks for the pre-PiP size on the first un-maximize instead. To check any of this, drive the real `Main.qml` with a different app id: the scripts match windows by app id, and a Flatpak and a dev run share `dev.skyline.Gravitas`, so a test run otherwise acts on the viewer's own window too.
- **Intro, recap and credits come from the file's own chapters, and only from their titles.** Streaming-service WEB-DLs name them (measured, Ted S1E7 FLUX: "Intro" 0:06-0:26, "Credits" 41:32), mpv lists them the moment the file opens (`MediaPlayer.chapters()`), and `application/segments.py` classifies them: skip buttons for intro/recap, and the next-episode card from the start of the credits (else the last 40s). Unnamed chapters ("Chapter 02") are never interpreted -- skipping someone past an episode's opening scene on a guess is worse than no button -- and position only settles titles that are ambiguous alone ("Credits"/"Générique" early is the opening). What the chapters leave out, SkipDB fills in (`infrastructure/metadata/skipdb.py`, the `SegmentSource` port): keyed by the Cinemeta video id's IMDb id/season/episode plus the file's duration (which lets it shift an answer recorded against another cut), asked **only** when the file does not name both intro and credits, and never over anything the file does name. Every lookup tells SkipDB what is playing, so each episode is asked once: an in-memory cache that also merges concurrent asks, then the shared `JsonDiskCache` (found answers 7 days, "nothing known" 1 day -- crowd data fills in), and **failures are never cached**. `online_segments` (on by default) turns it off; a late answer for a file already replaced is dropped by a per-file token. The timeline shows the same data: `segments.sections()` splits it at every chapter and at the intro/recap/credits edges (`PlayerController.timelineSections`), and `AppSlider` draws a sectioned track with a hover bubble only when it is given sections or a `hoverText` -- every other slider draws exactly as before.
- **The screen is kept awake by the app, not by mpv.** mpv's `stop-screensaver` only works when mpv owns the window, and with `vo=libmpv` it never does, so nothing told the desktop a film was playing and the screen dimmed mid-episode. `infrastructure/desktop/idle_inhibitor.py` implements the `IdleInhibitor` port per platform, and `PlayerController` holds it while a file is loaded and not paused (buffering counts as playing), re-checked on every `stateChanged`. On Linux: `org.freedesktop.ScreenSaver.Inhibit` first (it names the app in Plasma), then the portal's `Inhibit` (flag 8), which is the one that works inside the Flatpak and on GNOME. Both last only while the asking D-Bus connection stays open, and both take a `u` that **PySide6's QtDBus cannot marshal** (it sends `i` and the portal rejects the call), so this speaks D-Bus through `jeepney` on one worker thread. To check it on Plasma, read PowerDevil's `ActiveInhibitions` property **after about 5 s**: PowerDevil ignores shorter inhibitions, so an immediate read shows nothing even when it worked. `tests/conftest.py` stubs the backend so no test inhibits the developer's desktop.
- **QML reaches Python through typed singletons of the `Gravitas` module, never context properties.** `presentation/qml_module.py` is the one table of names → classes (`DetailController`, `StreamModel`, …); `main.py` hands the instances to `qml_module.bind(engine, {...})`, and QML writes `import Gravitas` and `DetailController.load(...)`. Context properties are invisible to tooling — qmllint reported all 700 uses as unqualified, so a misspelled method was a runtime TypeError on whichever screen ran it. Three things hold the scheme up. **Registration is per process but objects are per engine**: each name is registered once with `qmlRegisterSingletonType` and a provider that returns what *that* engine was bound, because tests build many apps in one process and a registered *instance* would leak the first app's (deleted) controllers into the next. **The runtime type is plain `QObject`**, so a test may bind a stub; the precise types live only in `qml/Gravitas/gravitas.qmltypes`, which nothing reads at runtime. **That file is generated** by `scripts/build_qml_types.py` from the same table, with PySide6's `metaobjectdump` + `qmltyperegistrar`, plus an AST pass for qasync's `@asyncSlot` (metaobjectdump does not know it, and without it every `load()` would be "missing"). Change a QML-facing Property/Signal/Slot and regenerate; the test suite fails on a stale file. The objects still need the keep-alive on `engine._gravitas_refs` — QML takes no ownership (the provider marks them `CppOwnership`).
- **Delegates declare what they read: `required property var model` / `int index` / `modelData`, under `pragma ComponentBehavior: Bound`.** Every file that has delegates or inline components carries the pragma, which is what lets a delegate reach the page's ids (`detail`, `stack`) with qmllint's blessing, and in exchange nothing is injected implicitly. Two consequences worth knowing. A required `index` still reads **-1 while the delegate sits in a reuse pool**, exactly like the old context property (checked against a `reuseItems` ListView), so PosterCard's and Home's `visible: index >= 0` hygiene is unchanged. And **an item loaded asynchronously by a `Loader` inside a delegate does not see the delegate's context** — read roles through the Loader (`rowLoader.model.title`), which is always reachable. Role names can no longer shadow page ids (roles are not injected), but `StreamListModel` keeps `extra` for its detail text. Reach for a typed assertion rather than a suppression when an API returns a base type: `(loader.item as ContextMenu)`, `p as Flickable`, `bar as AppScrollBar` — the codebase carries no `qmllint disable` comments, and a new one needs a reason the type system cannot express.
- **The native engine calls into Python from its own threads, so nothing in it may hold the GIL while waiting on them.** Events reach Python on the engine's event thread (`Python::attach`), and every binding call that can wait -- a load tears down the previous file's threads, a render scales a frame -- runs under `py.detach`. Dropping the engine joins that event thread, which may itself be waiting for the GIL to deliver a last event, so `shutdown()` releases the GIL first, and a `Player` collected without `shutdown()` drops on a thread of its own rather than in `tp_dealloc`. The binding takes a render buffer through the buffer protocol: a ctypes array exports no strides and PyO3 refuses it, so the item passes `memoryview(buffer).cast("B")`.
- **The native engine's video is pulled, and its end of file must not depend on anyone pulling.** The item asks for the frame due at the engine's clock on every `frameSwapped` while `wants_frames()` (plus a 50 ms kick timer, since a resume while nothing animates produces no frame to chain from), and the engine drops late frames there. A hidden window draws nothing, so the monitor also drops frames that are past due (`FrameQueue::drop_late`), and end of file is "the demuxer is done, audio has played out, and the last frame's time has come" -- not "the queue is empty", which never happened with nobody rendering and stalled the decoder on a full queue. Serials do the rest: every load and seek bumps one, and packets, chunks and frames of an older serial are dropped wherever they are found, so a seek never waits for a pipeline to drain. Its read-ahead is 30 s, so a pause longer than the proxy's `_WRITE_TIMEOUT_S` (30 s) stops it reading with the connection open; the proxy ends that connection as `_ClientStalled` (info, no traceback -- it is not a failure) and FFmpeg's `reconnect` picks the stream up again on resume, measured. mpv reaches the same path only after a longer pause, once its larger cache is full.
- **The native engine's zero-copy video is libplacebo on Qt's own Vulkan device, and its Qt side is C++.** `native/linux/gravitas_native_vk.cpp` (built into the same library as the mpv bridge) reads Qt's handles through QRhi, wraps the engine's images with `createFrom` + `createTextureFromRhiTexture`, and on `sceneGraphInvalidated` calls the engine's teardown directly -- no Python on the render thread at that moment, for the deadlock reason in the macOS-bridge note. Three facts it depends on: Qt enables every supported feature through the Vulkan **1.3** struct and none of 1.4's, so the bridge reports API 1.3 at most (told 1.4, libplacebo used push descriptors Qt never enabled -- caught by the validation layer); images replaced by a new size are retired, never destroyed before teardown; and engine logs reach Python from their own thread (`crates/python/src/logging.rs`), because a render-thread log taking the GIL deadlocks the same way. Never call `QQuickWindow.grabWindow()` from Python to check a Python-implemented video item: it waits for the render thread while holding the GIL, and the render thread needs the GIL for `updatePaintNode` -- a hang in the test, not in the item. Check with the validation layer instead (`QSG_RHI_DEBUG_LAYER=1 VK_LAYER_VALIDATE_SYNC=1`): what it reports today is inside libplacebo's upload of software-decoded frames, on its own device as much as on Qt's.
- **The native engine decodes on the GPU and copies each frame back; the hardware device is chosen, never assumed.** `crates/engine/src/hwdec.rs` sets `hw_device_ctx` + `get_format` before the decoder opens, in the order NVDEC (CUDA), VA-API, Vulkan on Linux (VideoToolbox on macOS; D3D11VA, CUDA, Vulkan on Windows), and `av_hwframe_transfer_data` + `av_frame_copy_props` bring every surface back with its colour tags and DV RPU, so everything after the decoder is unchanged. A stream the device cannot take is declined inside `get_format` and the same decoder carries on in software (H.264 High 10 on every decoder here), so whether hardware *engaged* is read off the frames: `Player::hardware_decoder()`, mpv's `hwdec-current`. `GRAVITAS_HWDEC` is shared with the mpv engine and read in mpv's names (`nvdec` → `cuda`, `-copy` dropped). Devices live on `Core` for the player's life and are made on a thread of their own while the first file opens (CUDA's ~150 ms was on the open path). Do not put VA-API ahead of CUDA: through nvidia-vaapi-driver it hangs in `vaSyncSurface` after a seek -- `ffmpeg -hwaccel vaapi -ss 1` hangs identically -- and a decoder stuck in a driver hangs `stop()`. Two test lessons: compare hardware and software pictures through libplacebo, not swscale (NV12 and planar take different swscale paths, mean 1.6/255 apart, while the decoded bytes are identical), and `Player` joins its `player-gpu` start-up thread on drop, because a process exiting while `pl_vulkan_create` runs aborted inside NVIDIA's driver.
- **The native engine's audio goes through cpal's PulseAudio host on Linux, and it must never be left to choose its buffer.** With the `pulseaudio` feature `cpal::default_host()` picks the PulseAudio host whenever a server answers (PipeWire serves one), else ALSA. Left at `BufferSize::Default` the server targets 2 s of buffer, which is 2 s between a load, seek, pause or audio switch and hearing it -- measured as the clock sitting at 0 for 2.2 s -- so `audio.rs::buffer_size` asks for a 20 ms period there. Multichannel output (5.1, 7.1) is only enabled on that host, because its channel map names the speakers (`OutputFormat::layout`: FFmpeg's `5.1(back)` and `7.1` in its order); everywhere else a multichannel buffer's order is a convention nobody here has checked, and a centre channel in the wrong speaker is worse than a downmix. That client (the `pulseaudio` crate) sends an EMPTY auth cookie when it finds none, where libpulse sends 256 zero bytes, and PipeWire refuses the empty one as `Invalid`: invisible wherever `~/.config/pulse/cookie` exists, silent in the Flatpak, which cannot see it -- cpal fell back to ALSA, whose pulse plugin is the host's and not in the runtime. `native_player.ensure_pulse_cookie()` points `PULSE_COOKIE` at a zero cookie before the engine starts when no real one is reachable. The pulse client library logs every connection at info and cpal's availability probe as an ERROR "Client disconnected"; `crates/python/src/logging.rs` passes that library's records on at debug. The engine also keeps libplacebo's compiled shaders on disk (`configure_shader_cache`, `cache_dir()/shaders`): 273 ms before the first picture of every launch without it, 12 ms with it.
- **The native engine reads network streams itself; the Python proxy is not in its path.** `crates/engine/src/net/` is the proxy's design moved behind FFmpeg's custom I/O (so a seek is a read position, not a connection): `CONNECTIONS` workers, runs of chunks on the aligned 1 MiB grid over a pooled `ureq` agent, the disk chunk cache, the backfill, the probe that never records a moment's failure as "no ranges", the fallback to FFmpeg's own client for a host without ranges and for a URL it failed on (`Global::note_broken`), and the refused-connect fast failure with the sinkhole check. Three things differ, each measured: a 429 hands the run back at once (a chunk must not wait out a backoff with a worker that cannot fetch it), the reader count drops straight to the requests the host is serving at that moment (not one per half second), and the read-ahead window starts at one run and grows with sequential reading (opening a file is scattered reads) -- except while paused, when it is the whole cache ahead, so a pause loads the file rather than the demuxer's 30 s (the demux loop passes the pause down, since it is the one thread still turning). A read takes bytes from a chunk still arriving. `main.py` wires `EngineStreamReading` as the accelerator when the native engine plays: `local_url` hands URLs back, `enabled` is the user's setting, and `NativePlayer.download_speed()` is the engine's `network_rate()` while the engine reads the file -- a 0.0 there is no sample, never a cue to read the demuxer's rate off the local cache (the 843 Mbps lesson below). Settings are process-wide (`configure_network`), so the Rust network tests run serially in a binary of their own. When timing first frames, take the time in the event callback: a render loop only notices after its current render returns, and the first libplacebo render compiles shaders (~160 ms), which once made the engine look 0.4 s slower than mpv (`vo=null` renders nothing).
- **A file's opening reads outlive the session, and must be restored before the demuxer sees its first bytes.** Resuming the same file reads the same header and index again through a new signed URL, so `crates/engine/src/net/keep.rs` keeps the chunks read before `Source::mark_opened` (size + FNV-1a of the first 64 KiB is the key; `EngineStreamReading` puts them in `<cache>-opening`, which `shutdown()` leaves alone -- a deliberate exception to "debrid bytes do not outlive their playback": a header and an index, capped at 32 MiB a file, 512 MiB in all). The key is gathered in `stream_body` from the bytes as they arrive, **not** from a finished chunk 0: the demuxer reads the header off a chunk still arriving and jumps to the index, so that run is abandoned before chunk 0 is ever whole. And those first 64 KiB are **held back** until they key the file, with the restore run before any of them is published: a Matroska header sits in the first few KiB, and published as it arrived the demuxer had jumped to the index before the key was complete -- on every other warm open at first, then one in three once only the restore moved ahead of publishing (1.27 s cold, 0.97 s warm, at 0.25 s a request). Resumes also start at the keyframe before the point (`LoadOptions::keyframe_start`, capped at `MAX_KEYFRAME_LEAD_S`): 2.09 s to 1.27 s on a file with four-second keyframes. A new file's audio decoder starts on `Core::audio_generation()`, never 0: the core's generation outlives files, and after a track switch in one file the next file's audio was all dropped as stale -- the clock held at the start behind a spinner, with minutes read ahead. Separately, `configure_network` forgets learned host limits: the rate-limit test taught `127.0.0.1` one reader for 15 minutes, and whichever test ran after it saw one connection.
- **The native engine switches audio tracks in place, and `aid`'s lessons do not carry over.** Its demuxer keeps every audio track's packets (`crates/engine/src/audio_queue.rs`, `KEEP_BEHIND_S` behind the playhead to the read-ahead), and the decoder reads the selected one through a cursor, so a switch between two tracks is a decoder swap at the playhead: `AudioPop::Switch` comes out of the queue ahead of the new track's first packet, `Core::audio_generation` marks what the old track had decoded, and the mixer drops that, lets the clock run on through the gap (`SWITCH_GRACE`), and trims the new track to when it is heard. No seek, no stall, ~50 ms to a full 100 ms of the new tone in the tests (`Player::recent_output` taps the output for exactly that check). Nothing like mpv's hot-audio graph is needed: only the selected track is decoded, so there is no track cap, no CPU per extra track and no sparse-track overflow. Turning audio off or back on still seeks. The audio tracks' bytes share `MAX_QUEUED_BYTES` with video, so several lossless tracks shorten the read-ahead in seconds.
- **On Linux/Vulkan the native engine makes the scene graph's device, and Qt adopts it.** Hardware decoding into the renderer's images needs a video decode queue on the device Qt draws with, and Qt creates its own with a graphics queue only. So `main.py` has the bridge create a `QVulkanInstance` (`gv_native_vk_instance`, GUI thread), the engine make a `SharedDevice` on it (`crates/libplacebo-sys/src/shared_device.c`) on a worker thread started as soon as the RHI is chosen (`_start_shared_device`: ~0.7 s, overlapped with the QML load and the app's wiring), and the window adopt it after `engine.load`, before the scene graph starts (`_adopt_shared_device`, `gv_native_vk_adopt` → `setGraphicsDevice`); the native engine is never put through mpv's GL/Vulkan interop probe (~0.3 s), which it has no use for: its Vulkan check is `gv_native_vk_gpu()`. With video zero-copy on that device the engine makes no Vulkan device of its own (`OwnRenderer::WhenNeeded`, `NativePlayer(zero_copy=True)`): an unused second device held Qt's render thread in NVIDIA's driver for ~0.8 s on the click that started playback, measured as the whole GUI freezing; `NativePlayer(shared_device=...)` then decodes into it and frames never leave the GPU. Three rules: the device enables what Qt's own would (every supported feature but robustness, Qt's optional extensions) because QRhi assumes them of an adopted device; FFmpeg uses an extension whenever it is enabled, feature or not, so only an explicit decode list is enabled and each has its feature struct on (validation caught `videoMaintenance1/2` used unenabled); and FFmpeg never gets the graphics queue, which Qt submits to without libplacebo's lock -- it is listed with only `VK_QUEUE_GRAPHICS_BIT`, for image sharing. The device and instance are never destroyed. A path that cannot sample it (swscale, the own-device readback renderer, a window that did not adopt it) copies the shown frame out (`hwdec::copy_to_memory`). The validation layer still reports FFmpeg's own `06811` (FFmpeg's own device does too) and intermittent `THREADING ERROR`s naming FFmpeg's frame threads, which an owner check on the lock showed never overlap -- do not chase those again without new evidence. Enabling `VK_{EXT,KHR}_swapchain_maintenance1` (libplacebo does, on its own) needs `VK_{EXT,KHR}_surface_maintenance1` on the instance, which the bridge adds. Measured at 4K HEVC 10-bit: 6% CPU against 30% copy-back, render-thread p95 0.23 ms against 5.3.
- **On macOS the native engine renders through Metal itself, and libplacebo is not in the build.** libplacebo has no Metal backend, Qt's scene graph is Metal there, and going through MoltenVK was ruled out, so `crates/engine/src/metal/` is a renderer of its own: one shader, parameters from `colour.rs`, VideoToolbox's `CVPixelBuffer`s wrapped as textures on Qt's own `MTLDevice` (decode, render and scene graph share the memory). **Nothing in it may be translated from libplacebo**: libplacebo is LGPL, the engine MIT, so HDR is BT.2390's EETF on BT.2100 ICtCp, Dolby Vision is ETSI GS CCM 001 with the fixed LMS matrix derived from HPE and BT.2020 in code, and the peak estimate and gamut compression are its own. SDR is the same standard arithmetic, so it matches libplacebo within 0.1 of an 8-bit step (libplacebo through MoltenVK is a macOS *test* dependency, the reference `metal::tests` compare against); HDR mid-tones come out brighter than libplacebo's spline by design. The HDR peak is measured on the GPU and never read back: histogram, then a one-thread pass that smooths it and writes the curve, then the draw, in one command buffer. Zero-copy ordering needs no fence -- the renderer commits to **Qt's own command queue** on the render thread, and Metal runs a queue in order with hazard tracking -- and nothing is torn down with the scene graph: the engine retains Qt's device and queue, and `native/macos/gravitas_native_metal.mm` retains every texture it wraps, because `QRhiTexture::createFrom` does not. Measured at 4K HEVC 10-bit: 0.41 ms (p95 0.54) per new frame on the render thread and 15% CPU, against 8.2 ms and 34% with VideoToolbox copied back. Two build facts: Apple's linker refuses an extension module's undefined `_Py*` symbols unless told (`crates/python/build.rs`), and `build_native_player.py` asks `cargo metadata` for the target directory, which a cargo config may move.
- **The player's format badges describe the file, read from its tracks -- and the audio profile comes from the decoder, not the header.** `track_list.media_format()` is the one reading for both engines (mpv's `track-list` shape, plus `color-transfer`, which mpv has as `video-params/gamma` and the native engine as a track field, and `hdr10-plus`, which only frames carry). Dolby Vision wins over the HDR10 base layer of a profile 8 file, and the hover says an HDR source is tone-mapped: the badge names the source, not the screen. The native engine opens files without FFmpeg's full probe, so a stream's header often leaves `profile` unknown; Atmos (E-AC-3 JOC, TrueHD) and DTS:X are what the *decoder* sets on its context once it reads the bitstream, so the engine publishes the running audio decoder's profile (`Player::audio_profile`) and the tracks report that for the playing track. Formats with a mark of their own show it: white copies of the Wikimedia Commons files (public domain, and DTS:X under CC BY-SA 4.0 with its attribution) vendored under `qml/formats/` by `scripts/vendor_format_logos.py`, which refuses a file whose recorded licence is not one the app may ship; the rest (HLG, resolutions, channels) are the icon font's glyphs. Copyright aside, every mark is its owner's trademark.
- **CoreAudio's playback timestamp through cpal leaves out the output stream's latency, so the mixer adds it.** 19.7 ms on a MacBook Air's speakers, measured, and where a Bluetooth sink reports its radio link; `crates/engine/src/coreaudio.rs` reads it for the default device every second, so a device change takes its own. The same module reads the device's preferred channel layout: a 6- or 8-channel device whose channels each name a distinct 5.1/7.1 speaker plays in its own order (the mixer permutes FFmpeg's), anything else plays stereo. Not yet tried on a real multichannel or Bluetooth output.
- **The native engine renders through libplacebo, on a Vulkan device of its own when it cannot use Qt's (everywhere but macOS).** HDR tone mapping and Dolby Vision (profile 5 included, from the RPU FFmpeg attaches to each frame) are libplacebo's; swscale draws until its device is up, and for good without one or after a failed render. `GRAVITAS_NATIVE_RENDERER=software` forces swscale. `NativePlayer.video_dolby_vision_profile()` answers 0 while libplacebo renders, because its callers warn about and remember releases that render wrong, and through libplacebo profile 5 does not. Two build details: libplacebo's FFmpeg helpers are inline C, compiled by `libplacebo-sys` from `src/libav.c`; and `pl_log_create` is a macro over a symbol named after the API version, which `libplacebo-sys` re-exports under the plain name so a different libplacebo still links.
- **QML has no unit tests beyond the lint gate and the component probes** — behaviour is verified at launch.
- **The test suite is offline, by construction.** `tests/conftest.py` replaces `socket.getaddrinfo` so any name but loopback fails at once. A test that builds the whole app gets the real bandwidth probe, and handed a fake stream URL it used to resolve it and wait out the probe timeout — about half the suite's runtime, and a result that depended on the machine's DNS. HTTP tests mock the transport (respx), the proxy tests serve on 127.0.0.1, and anything else that reaches for the network gets the same answer as an unreachable host. Wait for a condition, not a duration: `_drain_until` / `_pump_until` in the QML tests. `tests/conftest.py` forces `QT_QPA_PLATFORM=offscreen` for headless-safe Qt tests. `mypy --strict` covers `src` only; `python-mpv`/`qasync` are untyped, so precise `# type: ignore[...]` (with the specific code) is the norm, never blanket ignores.
- **On Windows python-mpv finds the DLL at *import* time, off `%PATH%`** (`mpv.py` scans for `mpv-2.dll`, `libmpv-2.dll`, `mpv-1.dll`) — there is no `ctypes.util.find_library` seam to patch as on Unix. So `_ensure_bundled_libmpv_findable()` prepends `sys._MEIPASS` to `PATH` instead of redirecting `find_library`, and it must run before `import mpv`. Same story for `yt-dlp`, which is bundled as `yt-dlp.exe` there.
- **Never hardcode `~/.local/share` & co. — use `infrastructure/paths.py`.** `config_dir()`/`data_dir()`/`cache_dir()` keep the XDG layout on Linux *and macOS* (moving macOS to `~/Library` would strand existing databases) and map to `%APPDATA%` / `%LOCALAPPDATA%` / `%LOCALAPPDATA%\Cache` on Windows. Both branches take `environ`/`platform` arguments so either can be tested from either host.
- **`QUrl(str)` is not `QUrl.fromLocalFile(str)`.** A Windows path parses as scheme `c:`, so `engine.load()` silently loads nothing. Anything handing a filesystem path to Qt must go through `fromLocalFile`.
- **The native engine on Windows is MinGW-built and loaded into an MSVC Python, and three Windows loader rules hold it together.** `build_native_player.py` builds it with MSYS2's UCRT64 Rust against libplacebo and libass from MSYS2 (pkg-config, so the `build.rs` files are the Linux ones) and the FFmpeg `scripts/build_ffmpeg_windows.py` builds from source into `build/ffmpeg-windows/` -- the same release as MSYS2's, with every built-in decoder, demuxer and protocol, the Windows hwaccels, dav1d, zlib and schannel, and nothing else: MSYS2's own links ~80 codec and encoder libraries and is GPL (x264/x265). Then it copies what the module imports into `gravitas_player.libs/`: 32 DLLs, 51 MiB, against 104 and 153 MiB with MSYS2's FFmpeg. The walk reads import tables with `objdump -p` and resolves each name itself, lean FFmpeg first -- `ntldd` searches its own directory, MSYS2's bin, before PATH, and so always answered with MSYS2's FFmpeg under the same file names. FFmpeg's HTTP is still in the path -- the engine's fallback for hosts it cannot read in ranges, and every addon subtitle file -- so schannel is not optional. Python never searches PATH for an extension's dependencies, so `infrastructure/player/__init__.py` registers that directory with `os.add_dll_directory` -- in the package, because a test or tool that imports the module directly passes through it too. The Vulkan bridge (`gravitas_native_vk.dll`, `gravitas_native_vk.cpp` alone, MSVC, because Qt's C++ ABI is MSVC's) links PySide6's `Qt6*.dll` and MSVC runtime, which a `ctypes` load does not search either: `native_vk_bridge` registers PySide6's directory around the load. And `subprocess` on Windows looks a program up on the *parent's* PATH whatever `env=` says, so the build scripts resolve `cargo`, `objdump` and `cl` with `shutil.which(..., path=env["PATH"])` -- and upper-case vcvars' environment, whose `set` dump spells it `Path`. A refused connect costs ~2s there (Windows retries the SYN twice), which the network test allows for. Not yet seen on a real GPU: the VM it was built on has no Vulkan driver, so only the D3D11 readback path has run.
- **Windows decodes video copy-back, not zero-copy** (mpv). The scene graph is pinned to OpenGL, which cannot import D3D11/DXVA2 surfaces, so `_default_factory` defaults `hwdec` to `auto-copy` there (`auto-safe` elsewhere) — otherwise mpv falls back to software decoding. `GRAVITAS_HWDEC` still overrides.
- **The spec's Qt payload filter must match both wheel layouts.** Unix keeps Qt under `PySide6/Qt/{lib,qml,plugins}` with `libQt6Foo.so`; Windows puts `Qt6Foo.dll` at the package root with the trees one level up. A `.so`-only regex ships a whole Chromium (QtWebEngine, ~200 MB) inside the Windows installer — the release job asserts it is gone.
